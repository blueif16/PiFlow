# SOTA brief: per-node optimization substrate (hard + soft measurement → issue release → rewind-proving → merge)

Date: 2026-07-05
Scope: pressure-test the proposed per-node substrate (attach to one finished node → hard measurements → soft LLM-judge critique → per-issue fix dispatch → self-rewind proving → merge) against the state of the art, 2024–2026. This is a research brief, not a design doc — recommendations are called out explicitly in the final section.

---

## 1. Programmatic/hard metrics over agent execution traces (agent observability)

**Findings.** The field has converged on two separate layers: a **schema** layer (OpenTelemetry's GenAI semantic conventions — `gen_ai.*` spans/attributes for operation name, request/response models, token usage split into input/output, finish reasons, and dedicated `execute_tool` spans) and a **detector** layer built on top of that schema (deterministic, non-LLM pattern matchers over the reconstructed call graph). The detector layer is the more directly reusable prior art: SentinelRCA ships 8 free, LLM-free detectors — `agent_loop` (same agent invoked 3+ times), `retry_storm`, `retrieval_without_grounding`, `missing_termination_condition`, `token_cost_runaway`, `latency_spike` (one span >50% of trace time), `sequential_tools` (parallelizable calls run serially), and `context_cache_opportunity`/`missing_session_memory` (unbounded input-token growth) — all computed by reconstructing the parent-child span tree and running graph algorithms, zero LLM calls. A harder research result: pure structural loop detection is weak on its own. "Unsupervised Cycle Detection in Agentic Applications" (arXiv 2511.10650) shows structural cycle detection alone scores F1 0.08, semantic-similarity detection alone F1 0.28, but the **hybrid** (structural pre-filter + semantic similarity on redundant content) reaches F1 0.72 — because agents loop *semantically* (regenerating similar-but-not-identical content) far more than they loop *structurally* (exact repeated call signatures). On the "does the agent even know it's burning budget" question, BAGEN (arXiv 2606.00198) found models predict "feasible" >70% of the time even after 60% of budget is consumed on runs that ultimately fail — the alarm fires too late to be useful from the agent's own signal, but an external early-stopping policy acting on the same trace saved 28–64% of tokens on doomed runs with only 1.6–4.2 points of success-rate cost. TRAIL (arXiv 2505.08638, Patronus AI) is the sobering ceiling check: even Gemini-2.5-Pro scores only 11% joint accuracy at localizing errors in annotated agent traces — meaning **LLM-based trace reading is currently unreliable as the *sole* hard-measurement mechanism**; the taxonomy (reasoning/execution/planning errors) is useful as a checklist, the "have an LLM read the trace" approach is not yet trustworthy alone.

**Named sources:**
- TRAIL: Trace Reasoning and Agentic Issue Localization — Deshpande et al., arXiv:2505.08638, https://arxiv.org/abs/2505.08638 (148 annotated traces, 841 errors, formal taxonomy, best model 11% accuracy)
- OpenTelemetry Semantic Conventions for Generative AI — https://github.com/open-telemetry/semantic-conventions-genai (spans, `gen_ai.usage.*`, `execute_tool` spans, agent/team/artifact proposal in issue #35)
- SentinelRCA — https://github.com/sentinelrca/sentinel (8 deterministic detectors over LangSmith/Langfuse/Phoenix/OTel traces)
- "Unsupervised Cycle Detection in Agentic Applications" — Felix et al., arXiv:2511.10650 (hybrid structural+semantic, F1 0.72 vs 0.08/0.28 alone)
- BAGEN: Are LLM Agents Budget-Aware? — arXiv:2606.00198 (late infeasibility recognition; 28–64% token savings from early stopping)
- "Early Diagnosis of Wasted Computation in Multi-Agent LLM Systems via Failure-Aware Observability" — arXiv:2606.01365 (online cheap signals + offline reliability/grounding metrics; 46–64% of wasted tokens spent *after* the first warning signal fires)

**BORROW:** Adopt OTel GenAI span/attribute names verbatim for the node's execution trace so hard measurements are portable and so any future off-the-shelf detector (Langfuse/Phoenix-style) can run against piflow traces without translation. Build the hard-measurement layer as a small library of **deterministic, LLM-free graph detectors** (à la SentinelRCA) run first, cheaply, on every node — loop/repetition, retry storms, cost-per-node outliers, token growth without corresponding progress — and treat "abnormally long thinking/sinking block" specifically as a **hybrid structural+semantic** check (repeated near-duplicate reasoning segments), not a pure length threshold, since pure-structural cycle detection is empirically weak (F1 0.08).

**AVOID:** Do not lean on an LLM to *read the raw trace end-to-end* and self-diagnose hard failures — TRAIL shows this fails even for frontier models on exactly this kind of task (trace debugging), and it is also the most expensive and slowest option. Hard measurement should stay non-LLM/graph-based; save the LLM for the soft-measurement stage where it has the golden artifact and a checklist to anchor against, not a raw span dump to interpret cold.

## 2. LLM-as-judge soft evaluation

**Findings.** Two questions dominate the 2025–2026 literature: (a) pairwise vs. pointwise reliability, and (b) how to get a judge to output *issues* rather than a *score*. On (a), the evidence is more nuanced than "pairwise is better because it's easier for the model" — it's actually the opposite on robustness. Tripathi et al. (arXiv:2504.14716, COLM 2025) show pairwise protocols flip preference 35% of the time under adversarial distractor features vs. 9% for absolute/pointwise scoring — pairwise is *more* exploitable because a generator can win by exploiting spurious features the judge over-weights in a head-to-head framing. Separately, "The Coin Flip Judge" (arXiv:2606.13685) ran 50 repeated trials per question and found pairwise preferences flip 13.6% of the time on identical re-judging (up to 56% for the worst question), while pointwise score *gaps* between two answers were statistically insignificant on average — meaning judges frequently declare a "winner" even when their own scalar scores show no real quality difference. Reliability curve analysis in the same paper found **11 repeated trials needed on average (15 for high-variance questions)** for a majority vote to recover the 50-trial reference verdict at 95% confidence — single-shot judging is measurably too noisy for a high-stakes gate. Rubric/checklist-based judging has its own bias, distinct from pairwise position bias: "Am I More Pointwise or Pairwise?" (arXiv:2602.02219) shows rubric-based scoring is implicitly a multiple-choice problem and exhibits primacy/recency position bias over the *rubric option list itself*; a balanced-permutation calibration measurably improves human correlation. On known biases broadly: position, verbosity, self-preference, and *style* bias are all separately documented and, per "Judging the Judges" (arXiv:2604.23178), **style bias dominates** (0.10–0.76 baseline) more than verbosity in a controlled 375-pair study, and verbosity bias direction is *model-specific* (Claude showed the opposite direction from Pro/Llama/Flash, GPT-4o was neutral) — meaning a single universal debiasing recipe doesn't transfer across judge models. On (b) — structured issue extraction — this is the most directly relevant sub-literature to the substrate design: "LLM-as-a-qualitative-judge" (arXiv:2506.09147) reframes judging around outputting a *structured report of common issue types* rather than a score, matching human-annotated issues in 2/3 of cases; CLEAR (AAAI 2026) does per-instance critique generation then clusters critiques via Key Points Analysis into a ranked, frequency-quantified issue list with drill-down to source instances; and a practitioner write-up ("Building an LLM Judge That Doesn't Lie to You") converges independently on the same architecture: **the judge classifies against a fixed violation catalogue with severity tiers and fixed point deductions; a separate deterministic engine does the arithmetic** — because "when the judge both finds problems and assigns scores, it conflates two tasks and does both poorly."

**Named sources:**
- Pairwise or Pointwise? Evaluating Feedback Protocols for Bias in LLM-Based Evaluation — Tripathi et al., arXiv:2504.14716 (COLM 2025) — pairwise flips 35% vs. pointwise 9% under distractor manipulation
- The Coin Flip Judge? Reliability and Bias in LLM-as-a-Judge Evaluation — arXiv:2606.13685 — 13.6% pairwise flip rate on identical re-trials; 11–15 trials needed for a reliable majority verdict; pairwise/pointwise disconnect
- Am I More Pointwise or Pairwise? Revealing Position Bias in Rubric-Based LLM-as-a-Judge — Xu et al., arXiv:2602.02219 — rubric-based judging has its own primacy/recency position bias; balanced-permutation fix
- Judging the Judges: A Systematic Evaluation of Bias Mitigation Strategies — arXiv:2604.23178 — style bias dominates over verbosity; verbosity bias direction is model-specific (Claude reversed vs. others)
- Self-Preference Bias in LLM-as-a-Judge — Wataoka et al., arXiv:2410.21819; DBG-score follow-up, ACL 2025 (aclanthology.org/2025.emnlp-main.86) — self-preference tied to perplexity/familiarity, not just identity
- Any Large Language Model Can Be a Reliable Judge: Debiasing with a Reasoning-based Bias Detector — arXiv:2505.17100 — external plug-in bias detector + iterative self-correction, +18.5% accuracy
- LLM-as-a-qualitative-judge — Chirkova et al., arXiv:2506.09147 — structured issue-type report instead of score; matches human-identified issues 2/3 of the time
- CLEAR: Error Analysis via LLM-as-a-Judge Made Easy — Yehudai et al., AAAI 2026 (doi.org/10.1609/aaai.v40i48.42398) — per-instance critique → Key Points Analysis clustering → ranked/quantified issue list
- TrustJudge — Wang et al., arXiv:2509.21117 — score-comparison and pairwise-transitivity inconsistencies in discrete rating systems; probabilistic scoring fix

**BORROW:** For the soft-measurement stage, make the judge's *only* output a structured, capped list of independent issues (id, severity, evidence, hinted suspect scope) — never a scalar score alongside it; if a score is needed downstream, compute it deterministically from the issue list (fixed severity weights), not by asking the judge for both simultaneously. For the golden-artifact comparison specifically, prefer **pointwise-against-reference with an explicit checklist** over freeform pairwise side-by-side — the evidence favors pointwise/rubric robustness against distractor exploitation, and reference-based framing (rate output vs. this specific golden artifact) is closer to pointwise-with-anchor than to open pairwise. If any comparison in the pipeline is genuinely pairwise (e.g., candidate-output vs. golden as two peers rather than the golden as ground truth), swap position and require agreement across both orderings before trusting the verdict — cheap and directly evidenced (Zheng et al.'s swap technique, cited across nearly every source above).

**AVOID:** Do not treat a single judge call's severity ranking as ground truth without at least a position-swap or multi-sample check on ambiguous/borderline issues — single-trial judging has a measured 13.6% flip rate on identical re-asks, and rubric-based judging has its own under-examined position bias over option ordering. Also avoid open-ended pairwise "which is better" framing for the golden-artifact comparison step specifically — it is the more exploitable, more distractor-sensitive protocol of the two, which cuts directly against the intent of comparing against a trusted reference.

## 3. Issue-decomposed repair

**Findings.** This theme has real, if largely SWE-bench/APR-flavored, prior art for the decompose→dispatch→isolate→merge shape, though it's mostly one-issue-per-run rather than one-run-with-N-parallel-independently-proven-fixes. SWE-Adept explicitly checkpoints (`hypothesis_git`) the original code state before repair, evaluates multiple competing repair *hypotheses* each on its own isolated branch, and only proceeds with a single hypothesis when root cause is unambiguous — this is the closest direct analog to "per-issue isolated proving." UniDebugger's hierarchical L1→L2→L3 escalation (simple fix → single-file fix → cross-file/cross-dependency fix, refining downstream-to-upstream on failure) is a useful triage-depth precedent for scoping a fix agent's blast radius by issue severity/complexity. On **merging independently-proven fixes and interaction effects** specifically — the part your design calls "interaction check" — the most direct evidence is DEIMerge, which shows that *naively picking the single best patch* underperforms *fusing repair clues from multiple (even individually-failed) patches*: their intelligent-merge step raised repair rate from 27.3% to 37.0% for single-patch selection, up to 57.3% overall by extracting and combining scattered signal across candidate patches — direct evidence that **combining fixes can outperform any single fix, but only with an explicit merge/fusion step, not a blind stack of diffs**. SYNFIX's "Synchrony" phase is the sharpest treatment of interaction effects: after patching a node, it walks one-hop neighbors in a dependency graph and re-checks/re-patches anything the first fix's ripple touches — an explicit acknowledgment that proving fix A in isolation does not guarantee fix A+B is safe. HARNESSFIX (arXiv:2606.06324) is architecturally close to your whole pipeline: diagnose failure → consolidate recurring diagnoses into flaw patterns → generate a scoped patch → **validate on a held-out split requiring both target-flaw improvement AND a regression ceiling** before accepting — i.e., a gate almost identical to your proposed GATE stage, just applied per-patch rather than post-merge. On "certain fixes skip proving" — the closest prior art is not agent-repair-native but security-autofix tooling: several autofix engines (a `FixConfidence` enum pattern seen across CodeGraph's autofix engine and similar OSS tools) grade fixes by *how the fix was derived* — AST-aware structural rewrites and template-matched fixes get high confidence and can auto-apply without further proof, while LLM-generated fixes are capped at low confidence and always require review/testing. The generalizable principle: **certainty should be earned by the fix's *provenance/mechanism* (deterministic transform vs. generative guess), not asserted by the fixer's own confidence claim.**

**Named sources:**
- SWE-Adept: An LLM-Based Agentic Framework for Deep Codebase Analysis and Structured Issue Resolution — OpenReview, https://openreview.net/attachment?id=1BLb4k0ETB&name=pdf — checkpoint-before-repair, competing hypotheses on isolated branches
- UniDebugger: Hierarchical Multi-Agent Framework for Unified Software Debugging — ACL/EMNLP 2025, aclanthology.org/2025.emnlp-main.921 — L1/L2/L3 escalating repair depth, reversed-order refinement on failure
- DEIMerge: An Automatic Program Repair Framework Based on Multi-agent Collaboration and Intelligent Patch Merging — Springer, doi 10.1007/978-981-95-7081-2_16 — merging failed-patch clues raises repair rate 27.3%→37.0% (up to 57.3%)
- HARNESSFIX: From Failed Trajectories to Reliable LLM Agents — arXiv:2606.06324 — diagnose→consolidate→scoped-patch→validate-with-regression-ceiling pipeline for agent harness repair
- SYNFIX: Dependency-Aware Program Repair via RelationGraph Analysis — ACL Findings 2025, aclanthology.org/2025.findings-acl.252 — "Synchrony" phase re-checks one-hop dependency neighbors after a patch to catch interaction effects
- DIAGPaper: Diagnosing Valid and Specific Weaknesses in Scientific Papers via Multi-Agent Reasoning — arXiv:2601.07611 — Prioritizer ranks top-K weaknesses; adversarial Rebuttal module filters 40–60% of invalid/unsupported critiques before they reach the fixer
- CodeGraph Autofix / representative `FixConfidence` pattern (codegraph.ru/docs/en/guides/02-security-audit-autofix.html) — confidence tied to fix *mechanism* (SSR/template = auto-apply tier, LLM-generated = always-review tier), illustrative of the "certain fixes skip proving" idea, though from security-autofix not agent-repair literature

**BORROW:** Adopt SWE-Adept's checkpoint-then-isolated-branch-per-hypothesis pattern directly for the rewind-proving stage — it is exactly your "self-rewind" mechanism, already validated in an SWE-bench-adjacent setting. Adopt DIAGPaper's adversarial Rebuttal-before-Prioritizer step as a candidate addition upstream of ISSUE RELEASE: before dispatching a fix agent per issue, have a cheap adversarial pass challenge each soft-measurement issue (is this really wrong, or is the judge hallucinating a defect?) — DIAGPaper measured this step removing 40–60% of initially "identified" weaknesses, which is a large false-positive rate to not be filtering. For MERGE, explicitly borrow SYNFIX's one-hop dependency check as the mechanism for the "interaction check" stage rather than a blind combined-run: cheaper than a full re-run and it tells you *which* fixes are likely to interact before you pay for the combined execution. For "certain fixes skip proving," gate exemption on the fix's *mechanism* (e.g., a fix that only changes a config value the golden artifact and checklist both explicitly require, or a fix generated by a deterministic template) rather than on the fixer agent's self-reported confidence — self-reported confidence from a generative fixer is not evidenced as trustworthy anywhere in this literature.

**AVOID:** Do not pick "the single best fix" among competitors and discard the rest — DEIMerge's core finding is that discarded/failed candidates still carry usable repair signal that a fusion step can recover; a pure winner-take-all issue-release design leaves real quality on the table. Do not skip the post-merge interaction check on the assumption that N independently-proven fixes compose safely — SYNFIX and HARNESSFIX both build explicit machinery specifically because that assumption fails in practice (a fix's local correctness doesn't guarantee no dependency-level ripple with a sibling fix).

## 4. Replay/rewind of agent runs as an evaluation harness

**Findings.** A small but concrete cluster of 2025–2026 tools has converged on the same architecture for deterministic agent replay: intercept every non-deterministic host call (LLM sampling, tool calls, clock, RNG) at the point of use, log it with a sequence number, and on replay serve recorded values instead of live calls up to the point where you inject a change — only steps *downstream of the change* re-execute live. Chidori pins `Date`/`Math.random` and routes all side effects through a logged host function; "Rewind" explicitly frames this as "fork at step N, steps 1..N-1 served from cache, step N+ live," and reports token/dollar/time savings per replay; `stepback` is the most mechanistically precise: it treats each recorded step as a **content-addressed computation over canonical inputs**, so a substitution's effect propagates through a **dirty-set** dependency graph and only genuinely-affected downstream steps re-run (not everything after the injection point positionally, but everything actually *data-dependent* on it) — this is a materially better model for your "replay the node with only one fix applied" stage than a naive "replay from step N onward." `agenticstash` adds a useful failure mode to plan for: **divergence detection** — if a call's *input* no longer matches the recording (because your fix changed upstream behavior in a way the original trace didn't anticipate), replay must fail loudly (`ERR_DIVERGENCE`) rather than silently falling through to a stale cached response, which would silently corrupt the isolation guarantee the whole rewind-proving stage depends on. On the **noise problem** specifically — how many replays for a fair delta — the most quantified answer available is from the judge-reliability literature rather than replay-specific literature, but it transfers directly: "The Coin Flip Judge" found **11 repeated trials on average (15 for high-variance cases)** needed for a majority-vote verdict to match a 50-trial reference at 95% confidence, and separately, LLM A/B-testing guidance (GrowthBook, and independent statistical-power write-ups) converges on **200–500 samples as a pilot floor** to even *measure* the true variance before you can size a real test, with required sample sizes for detecting a genuine few-point quality delta running into the thousands per arm under standard power assumptions — orders of magnitude more than a single-replay or even 2–3-replay comparison can support. Paired analysis (comparing the same input across both conditions rather than independent samples) is the one lever that meaningfully cuts this — it roughly halves the required sample size because it exploits shared per-question difficulty/variance, which is directly applicable since your rewind-proving stage is inherently paired (same node input, with-fix vs. without-fix).

**Named sources:**
- Chidori "Checkpoint & Replay" docs — https://thousandbirds.ai/docs/concepts/time-travel — deterministic-by-policy replay via logged host functions, sequence-numbered call log
- agentoptics/rewind — https://github.com/agentoptics/rewind/blob/HEAD/docs/replay-and-forking.md — fork-and-execute replay, cached-up-to-divergence, quantified token/cost savings per replay
- thehalleyyoung/stepback — https://github.com/thehalleyyoung/stepback — content-addressed step cache, dirty-set propagation through a dependency graph, `bisect`/`branch_at`/`compare_branches` API
- davccavalcante/agenticstash — https://github.com/davccavalcante/agenticstash — divergence detection (`ERR_DIVERGENCE`) when a replayed call's input no longer matches the recording
- The Coin Flip Judge? — arXiv:2606.13685 — 11–15 replays needed for a reliable majority-vote verdict (transfers directly to "how many reruns for a fair rewind-proving delta")
- "How do you A/B test an LLM when outputs aren't deterministic?" — GrowthBook, https://www.growthbook.io/insights/ab-testing-llms — heteroskedastic variance (5–10% divergence on easy tasks, 40–60% on hard reasoning tasks), 200-sample pilot-floor guidance
- "Your LLM Eval Is Lying to You: The Statistical Power Problem" — tianpan.co, 2026-04-15 — paired analysis halves required sample size vs. independent-sample comparison; worked example of required-N scaling with target delta size

**BORROW:** Adopt the content-addressed, dirty-set-propagation replay model (stepback) rather than a simpler "replay from step N onward" positional model — a fix applied early in a node's execution may only actually affect a subset of downstream calls, and re-running only the genuinely-affected subset is both cheaper and a more honest isolation of "what did this fix actually change." Build in explicit divergence detection as a first-class signal, not a silent fallback: if a fix changes upstream behavior enough that a downstream cached call's recorded input no longer applies, that should surface as "this fix's blast radius is larger than assumed" rather than silently reusing stale cache. For the noise problem, treat rewind-proving as inherently **paired** (same node input under with-fix vs. without-fix) and budget for **multiple replays per candidate fix, not one** — a single before/after replay pair is exactly the underpowered single-trial comparison the LLM-judge-reliability and LLM-A/B-testing literature both independently warn against; 3–5 paired replays is a defensible floor grounded in the 11–15-trial finding scaled down by the paired-analysis variance reduction, not a made-up number, but should be validated empirically per fix-class rather than assumed.

**AVOID:** Do not accept a single-replay "improved" / "regressed" verdict as proof for any fix class where the node's underlying execution has real LLM-sampling variance (i.e., anything except a fully deterministic mechanical fix) — the literature is unusually consistent that single-sample deltas on stochastic LLM behavior are noise-dominated, and treating one lucky/unlucky replay as ground truth is the single most evidenced pitfall across this whole theme. Also avoid silent cache reuse on divergence — the isolation guarantee of rewind-proving depends entirely on "only the fixed thing changed," and silently serving a stale cached value on a mismatched input silently breaks that guarantee without any visible signal that it happened.

## 5. Prompt/agent optimizers as prior art

**Findings.** DSPy's MIPROv2 and GEPA represent two different philosophies your severity-ranked-issue-release design should be positioned against. MIPROv2 treats prompt optimization as **black-box Bayesian optimization** over a joint space of instructions and few-shot examples, scored purely numerically — it never looks at *why* a candidate scored low, only *that* it did. GEPA (arXiv:2507.19457) is the more directly relevant precedent: it's explicitly **reflection-driven**, requires the metric to return `(score, feedback)` rather than just a score, and that feedback string is what actually drives the LM's next instruction edit — GEPA beats MIPROv2 by >10% (e.g., +12% on AIME-2025) specifically because natural-language feedback carries more actionable signal per optimization step than a scalar. GEPA also formalizes a design choice worth noting: it deliberately uses **two different models for two different roles** — a cheap model for frequent evaluation, and a separately-configurable, typically stronger `reflection_lm` for the comparatively rare "propose a new instruction from failure feedback" step — because reflection is a harder, less-frequent, quality-sensitive operation than plain scoring. Self-Refine's ablation is the single clearest evidence in this whole brief that **feedback specificity is not a nice-to-have but the dominant variable**: in their Sentiment Transfer task, specific/actionable feedback scored 43.2, generic feedback scored 31.2, and no feedback failed the task outright — a ~40% relative gap driven purely by feedback specificity, holding the model and task fixed. This directly validates your soft-measurement stage's design goal (specific, evidenced, per-issue feedback) over a simpler holistic critique. Reflexion contributes the cross-episode framing and a documented failure mode: it could not escape local minima on tasks (WebShop) requiring genuinely creative/diverse exploration to break out of a repeated bad strategy — a caution that reflection-based self-correction has a ceiling when the fix requires exploring outside the space the agent has already tried, not just refining within it. On concrete stopping/gating mechanics for iterative critique-refine loops, informal-but-consistent practitioner guidance (echoing the published Self-Refine/Reflexion shape) converges on: cap iterations low (3 is the reported practical default, evidence for iteration-4+ gains is rarely present when actually measured), require an explicit halt signal from the critic rather than parsing free-form "looks good," and separately detect "no progress" (byte-identical output across iterations) and "oscillation" (reverting between two prior outputs) as distinct early-exit conditions — both of which are failure modes a single "did the score improve" check would miss. Anthropic's own public guidance (Building Effective AI Agents) frames the evaluator-optimizer pattern as appropriate specifically when "LLM responses can be demonstrably improved when a human articulates their feedback, and the LLM can provide such feedback" — and repeatedly stresses **add complexity only when it demonstrably improves outcomes**, i.e., don't build the full severity-ranked/issue-decomposed machinery for node classes where a single evaluator pass already saturates quality.

**Named sources:**
- GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning — arXiv:2507.19457; DSPy docs at dspy.ai/api/optimizers/GEPA — feedback-shaped metric contract `(score, feedback)`, separate `reflection_lm` vs. `task_model`, Pareto-frontier candidate selection, beats MIPROv2 by 10%+
- MIPROv2 — dspy.ai/api/optimizers/MIPROv2 — Bayesian optimization over instructions + few-shot demos, purely score-driven (no feedback channel)
- Self-Refine: Iterative Refinement with Self-Feedback — Madaan et al., arXiv:2303.17651 — actionable vs. generic feedback ablation (43.2 vs. 31.2 vs. task failure with no feedback)
- Reflexion: Language Agents with Verbal Reinforcement Learning — Shinn et al., NeurIPS 2023, https://proceedings.neurips.cc/paper_files/paper/2023/file/1b44b878bb782e6954cd888628510e90-Paper-Conference.pdf — episodic verbal-RL memory; documented WebShop failure to escape local minima requiring creative exploration
- Building Effective AI Agents — Anthropic, https://www.anthropic.com/research/building-effective-agents (and the accompanying cookbook notebook anthropics/claude-cookbooks, patterns/agents/evaluator_optimizer.ipynb) — evaluator-optimizer pattern, PASS/NEEDS_IMPROVEMENT/FAIL structured verdict, "add complexity only when it demonstrably improves outcomes"
- "When AI builds itself" — Anthropic, https://www.anthropic.com/institute/recursive-self-improvement — recursive self-improvement research note; human-defined scoring rubric as the one fixed point, agents design their own experiments within it

**BORROW:** Adopt GEPA's `(score, feedback)` metric-contract shape at the interface between your SOFT MEASUREMENT stage and each fix agent — every issue dispatched to ISSUE RELEASE should carry not just its severity/scope hint but an explicit, evidenced feedback string (why this is wrong, what the golden artifact does differently), mirroring the Self-Refine finding that this is the single highest-leverage lever available. Adopt GEPA's two-tier model assignment as a cost-control default: a cheaper model for the frequent hard-measurement/soft-measurement scoring pass, a stronger model reserved for the comparatively rare "propose the actual fix" step. Borrow the explicit halt/no-progress/oscillation triad for any stage of your substrate that iterates (e.g., if a fix agent gets multiple attempts at one issue) rather than relying on a bare score-improved check, since score-improved alone misses both the "stuck oscillating between two bad states" and "silently made no change" failure modes.

**AVOID:** Do not let the substrate's sophistication grow unconditionally — Anthropic's own framing (and Reflexion's documented ceiling on tasks needing real exploration rather than refinement) both caution that this class of machinery has a domain where it stops paying for itself: nodes whose failures are exploration/creativity-limited rather than correction-limited won't be well served by iterative critique-refine, and nodes that already pass a single evaluator check don't need the full per-issue decomposition and rewind-proving apparatus at all. Treat "does this node class benefit from the full substrate" as a gate, not an assumption.

## Design implications for the substrate

Mapped to the five stages named in the brief: **hard** (programmatic measurement), **soft** (LLM-judge critique), **issue-release** (dispatch), **rewind-proving** (isolated re-run), **merge** (combine + interaction check).

1. **[hard]** Build hard measurements as deterministic, LLM-free graph/statistical detectors over an OTel-GenAI-shaped trace (loop/repetition, retry storms, token-growth-without-progress, latency outliers) — do not ask an LLM to read the raw trace cold; TRAIL shows even frontier models are unreliable at that specific task (11% accuracy).
2. **[hard]** For "abnormally long thinking/sinking block" specifically, implement it as a hybrid structural+semantic check (near-duplicate reasoning segments), not a pure length/token threshold — pure structural loop detection alone is empirically weak (F1 0.08 vs. 0.72 hybrid).
3. **[soft]** Make the judge's sole output a structured, capped, severity-tagged issue list (id, evidence, hinted scope) with feedback text per issue — never a bundled scalar score from the same call; if you need a score, derive it deterministically from the issue list, mirroring the consistent "separate classification from arithmetic" finding across CLEAR, the qualitative-judge paper, and practitioner write-ups.
4. **[soft]** Frame the golden-artifact comparison as reference-anchored/pointwise-with-checklist rather than open pairwise — pointwise is measurably more robust to distractor/style exploitation (9% vs. 35% flip rate under manipulation), which matters more here than in a generic leaderboard setting because your reference artifact is meant to be authoritative, not just "the other candidate."
5. **[soft]** Add a cheap adversarial "is this issue really valid" filter between soft measurement and issue release, borrowed from DIAGPaper's Rebuttal module — it removed 40–60% of initially-flagged weaknesses in that setting, which is too large a false-positive rate to skip filtering before spending fix-agent budget on each issue.
6. **[issue-release]** Gate "certain, no-proof-needed" fix classes on the fix's *mechanism/provenance* (deterministic/templated transform, or a change the checklist+golden artifact both unambiguously require) rather than on any self-reported confidence from a generative fixer — no source in this brief evidences generative self-confidence as trustworthy for auto-apply decisions.
7. **[rewind-proving]** Implement isolated re-run as content-addressed replay with dirty-set propagation (stepback's model), not positional "replay from step N" — a fix's actual blast radius through the node's execution graph is what should determine what re-runs, and mismatched replay inputs should raise a loud divergence signal rather than silently reusing stale cache.
8. **[rewind-proving]** Budget multiple paired replays per candidate fix (not one), sized from the judge-reliability finding that 11–15 trials are needed for a stable majority verdict, discounted for the fact that rewind-proving is inherently paired (same node input, with/without fix) which the LLM-eval-power literature shows roughly halves the required sample count versus independent sampling. Treat a single before/after replay delta as inconclusive by default for any fix class touching a stochastic step.
9. **[merge]** Do not assume N independently-proven fixes compose safely — run an explicit interaction check modeled on SYNFIX's one-hop dependency-neighbor re-verification (cheaper, targeted) before or alongside a full all-fixes-combined run, and consider DEIMerge's finding that fusing signal from multiple fixes (including ones that individually underperformed) can beat picking any single best fix outright.
10. **[all stages]** Gate the whole substrate's invocation per node-class: per Anthropic's own guidance and Reflexion's documented ceiling, apply the full hard→soft→issue-release→rewind-proving→merge machinery only where a node's failure mode is genuinely correction-shaped (an evaluator can articulate what's wrong and a fixer can act on it) — nodes that already pass a lighter single-pass check, or whose failures need exploration rather than refinement, shouldn't pay this cost.

---

**Coverage note on thinness:** Theme 3's "certain fixes skip proving" sub-question is the one place where directly-on-point prior art (agent-repair-native, not just security-autofix-adjacent) is genuinely thin — the confidence-tiering pattern cited there comes from vulnerability-autofix tooling (CodeGraph, pfix, similar), not from an agent-optimization-loop paper. The generalizable principle (gate on fix mechanism/provenance, not fixer self-confidence) is sound and worth carrying over, but it is an analogy from an adjacent field rather than a direct precedent, and is flagged as such above rather than presented as agent-repair-specific evidence.
